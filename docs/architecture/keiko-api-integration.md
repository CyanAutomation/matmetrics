# Keiko API Integration

## Contract source and pin

Keiko Dojo owns the REST contract in `openapi.yaml`. This MatMetrics revision pins source repository `https://github.com/CyanAutomation/keiko-dojo`, commit `93676b9475657044378b895ac3f30b67a6b3b31b`, file `openapi.yaml`. A byte-for-byte snapshot is stored at `src/lib/keiko-api/openapi.yaml`; `metadata.ts` records the source revision, SHA-256, generator, and command. CI checks the snapshot checksum and regenerates `generated.ts`. Consumers do not follow Keiko `main` implicitly.

To update the contract, review a Keiko contract commit, copy that commit's `openapi.yaml` snapshot, update its immutable source SHA and checksum in `metadata.ts`, regenerate with `npm run keiko-api:generate`, inspect the generated diff, and run `npm run keiko-api:check`. Do not hand-edit `generated.ts` or transport output.

## Typed client boundary

`src/lib/keiko-api/generated.ts` is generated by `openapi-typescript@7.13.0`. `client.ts` uses `openapi-fetch@0.14.1` with Fetch and the generated `paths`/`components` types. It covers session listing, detail, create, update, and delete. The adapter returns the upstream `Response` plus a clone for the existing façade, preserving status, body, and headers without introducing Axios or a framework dependency.

Keiko's `SessionRecord` maps explicitly to the MatMetrics facade. Its `session` becomes the frontend session object and its numeric `revision` becomes `keikoRevision`. That field is never treated as GitHub `revisionSha`. The façade still validates session record shape before mapping. ETags, `If-Match`, 404, 409, 412, 428, authentication errors, `Retry-After`, and request IDs are preserved. Missing `If-Match` is intentionally allowed through the local typed adapter so Keiko can return its documented 428 response.

## Authentication and same-origin façades

Browser requests continue to use MatMetrics same-origin `/api/sessions` routes. The server verifies the existing `matmetrics-api` JWT and Better Auth session, exchanges them for a short-lived scoped Keiko token, and sends only that token to Keiko. The adapter runs only on the server gateway. Better Auth cookies and service credentials are never forwarded to Keiko or exposed to browser code. The verified principal and Keiko authorization continue to determine user scope; client IDs are resource identifiers, not tenant selectors.

The generated contract is independent of Next.js, React, Better Auth, and UI state. Existing guest and legacy GitHub/Go paths continue through their current storage routes. Analytics and GitHub operations remain in the existing gateway, with adoption limited to the training session CRUD boundary in this phase.

## Errors and revisions

HTTP responses keep their original status. The server façade keeps safe error bodies and forwards `ETag`, `Retry-After`, `WWW-Authenticate`, and `X-Request-Id` when present. Transport failures become the existing service-unavailable façade response; diagnostics log only safe error names. Rejected mutations are not retried with a newer revision, and create requests are not automatically replayed.

## Future Companion use

A future Companion can consume the same canonical OpenAPI source and generate an independently pinned TypeScript client. It will need its own same-origin API façade and authentication integration. This phase does not add a shared package, cross-origin credentials, offline outbox, or Companion application.
